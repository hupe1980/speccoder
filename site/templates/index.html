For GitHub Spec Kit projects

Spec-driven coding,
decided by evidence.

speccoder implements your feature task by task. Before each attempt it turns the spec's acceptance examples into tests that must fail; after it, it runs your checks and audits the diff. A task is ticked only when the evidence holds — never on the model's word.

A coding agent that cannot mark its own homework

Agents are good at writing code and too good at declaring victory. speccoder separates the two: a model proposes, and code decides.

  1. 1

    Ready

    The next task whose dependencies in tasks.md are met.

  2. 2

    Red

    Tests derived from the spec's acceptance examples, which must fail now. The implementer cannot change them.

  3. 3

    Attempt

    The model works in an isolated worktree. Every tool call is allowed, sent to you, or denied — before it runs.

  4. 4

    Judge

    Your checks again, the acceptance tests green, and an audit that catches deleted or weakened tests.

  5. 5

    Record

    A passing task is ticked and committed. Everything else is saved in git and undone, and you decide.

Everything around the model, done properly

Evidence decides

verified means spec-derived tests went red → green and nothing regressed. Optional mutation testing and a reasoning-blind gaming monitor catch tests written to pass.

Spec Kit native

Reads spec.md, plan.md and tasks.md as Spec Kit 0.13–1.2 write them, runs Spec Kit's planning skills, its extension hooks and its workflow engine.

Isolated and sandboxed

Work happens on speccoder/<feature> in its own worktree. Commands run in an OS sandbox: no writes outside, no credentials, no network.

Every call governed

A policy classifies each call before it runs. Approvals are inline, in your editor or later — and every decision records who made it.

Durable and replayable

Every model and tool call is journaled. A killed run resumes without repeating finished calls; any recorded run replays offline, without a model.

Your model, or your agent

Anthropic, OpenAI or a local OpenAI-compatible server — or let Claude Code or Codex make the attempts and keep speccoder's judgement.

Built to scale out

Run independent [P] tasks in parallel worktrees, verified together after merging; keep the best of several attempts by evidence.

Ready for review

Hand off a draft pull request whose description is the evidence behind every tick. speccoder never merges.

From spec to verified branch in minutes

You need git, a Spec Kit project and a model. speccoder reads committed files only, so your configuration is reviewed like code.

Read the quickstart 
# detect your checks, review, commit
speccoder init && speccoder verify
git add -A && git commit -m "speccoder config"

# key from the environment only
export OPENAI_API_KEY=…

speccoder run      # task by task, with evidence
speccoder report   # the evidence behind every tick
git merge speccoder/001-my-feature

What verified does not mean

It means the acceptance tests derived from your spec went from red to green and no check regressed. It does not mean the change is correct, complete or safe. speccoder makes review cheaper and better informed; it does not replace it. When it cannot demonstrate something — a gap no failing test shows, a task that contradicts its spec — it stops and says so instead of guessing.
