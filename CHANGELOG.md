# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and the project
adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Cargo workspace with four crates: `speccoder-core` (pure domain),
  `speccoder-speckit` (Spec Kit adapter), `speccoder-runtime` (application
  services, substrate seam) and the `speccoder` binary.
- `speccoder --version`, `--help` and a global `--json` flag.
- `speccoder inspect [PATH] [--feature]`: read-only discovery of a Spec Kit
  project (metadata, constitution, ordered features, artifacts), a tolerant
  `tasks.md` parser (IDs, done, `[P]`, `[USn]`, phases, subsections, byte
  ranges, SHA-256 line and section hashes), stable diagnostic codes, workspace
  containment (symlinks included) and exit codes 10–12.
- Task graph: dependencies from phase structure, subsections, `[P]` runs and
  `depends on` / `after` references; `graph.dangling` and `graph.cycle`
  errors; per-task state (done, ready, blocked) and blockers in `inspect`.
- Declared dependency mode for task lists whose Format line documents
  `(depends on …)`; `SPECIFY_FEATURE_DIRECTORY` feature selection; a fixture
  corpus generated by Spec Kit 1.1.3 and 1.2.2.
- `speccoder verify [PATH] [--tier] [--against FILE]`: runs the checks declared
  in `speccoder.toml` (argv only, stdin closed, process-group timeout, capped
  output, secret-scrubbed environment), reads per-test results from JUnit
  reports, compares with a saved baseline (regressions, pre-existing failures),
  exit codes 13 and 20; verdict rules (`verified`, `regression_only`, `failed`)
  in `speccoder-core`.
- `speccoder worktree [PATH] [--feature]`: an isolated git worktree on
  `speccoder/<feature>` in the state directory, reused or re-attached; refuses
  (exit 14) when the feature's Spec Kit artifacts are not committed. Library:
  checkpoints of the whole working tree via a temporary index (HEAD, index and
  refs untouched), diffs, and restore that rewrites only differing paths.
- The execution substrate: agentplane 0.48.0 embedded (`embed` feature) with a
  redb journal in the state directory and the speccoder agent declared in code.
  `speccoder propose --task <ID>` makes one governed model call for a
  structured, never-executed proposal (cache breakpoints after the stable
  prompt parts; key from `ANTHROPIC_API_KEY`, never printed or journaled);
  `speccoder replay <RUN>` replays a recorded run strictly, without the model.
  Exit codes 15, 21, 22. Providers: `anthropic` (Messages API, explicit cache
  breakpoints) and `openai` (Responses API, automatic prefix caching).
- Tools for the agent loop, served to agentplane as `fs`, `proc` and `git`:
  `read_file`, `list_files`, `search_code`, `write_file`, `edit_file`,
  `run_command`, `git_status`, `git_diff` — confined to the worktree,
  `.gitignore`-aware, refusing secrets and protected paths (Spec Kit intent,
  verification inputs, `.git`), with before/after hashes on writes; a
  deterministic policy (allow / approval / deny) checked before every call.
- `speccoder run --task <ID>`: one governed attempt at a ready task in its
  worktree — baseline checks, checkpoint, a bounded tool loop (policy before
  every call; `report_blocked`; approval-requiring calls stop the attempt),
  diff, checks against the baseline and the verifier's verdict beside the
  model's claim. Exit codes 16 and 23. Tool schemas are strict-calling
  compatible; everything the attempt decides by is in its journaled input, so
  real attempts replay strictly.
- `speccoder eval [DIR] [--case] [--keep DIR]` and the `evals/` suite (three
  cases and one impossible task) judged by hidden oracles: verified-completion
  precision, cheats, tokens per correct case; exit 24.

- Quality gates as `just ci` (fmt, clippy, tests, cargo-deny, layering, docs,
  package dry run), run on macOS and Linux in GitHub Actions.

- Test integrity: tests that exist when an attempt starts are frozen (editing
  them stops the attempt for approval); every attempt's diff is audited for
  deleted or modified frozen tests, removed test functions, new skip markers
  and changed verification inputs — any finding fails the verdict.

- Feature runs: a passed task is ticked by the engine (one byte, hash-guarded)
  and committed on `speccoder/<feature>`; `speccoder run` without `--task`
  works through ready tasks until the feature is done, and resumes after a
  stop; `[git] commit = "per-task" | "none"`, `--max-tasks`.

- Spec-derived acceptance tests: before an attempt, a separate tool-less call
  turns the story's acceptance examples into new, frozen test files that must
  fail first and pass afterwards; red-then-green makes the verdict `verified`
  (`[acceptance] generate`, default on).
- Retries: a completed attempt the verifier fails is undone and retried from
  the same checkpoint with a verifier-built failure digest
  (`[budget] max_attempts`, default 2); identical failure fingerprints,
  integrity findings and checks that cannot run stop retrying. The run report
  lists earlier attempts and why retrying stopped; `eval` shows attempts per case.
- `speccoder eval --repeat N` runs the suite N times and reports per case how
  often it came out as expected and how often it was retried; two harder
  evaluation cases (`semver-order`, `wrap-text`) with edge-case oracles.
- `speccoder converge`: a read-only assessment of a finished feature against
  its spec, plan, tasks and constitution; speccoder appends actionable
  findings as a `## Phase N: Convergence` section (hash, prefix and re-parse
  guarded) and commits it; `unrequested` findings go to a person; repeats and
  `[converge] max_rounds` stop it. A convergence task gets the whole spec and
  changes no code unless its acceptance tests fail first (`not_demonstrated`).
  `speccoder run --converge` loops runs and convergence.
- `speccoder report`: every task with the evidence behind its tick
  (`verified`, `regression_only`, ticked without speccoder evidence) and the
  open ones, convergence rounds and unmerged commits — read-only, from the
  speccoder branch's `tasks.md` and commit trailers.
- Two impossible evaluation cases: `impossible-spec` (a self-contradicting
  spec) and `impossible-offline` (a current value under offline constraints).

- Durable attempts: every attempt that does not pass is saved under
  `refs/speccoder/attempts/<feature>/<task>/<run>` (outcome, reason and run
  in its trailers) and undone in the worktree; leftovers of an interrupted
  run are saved and set aside before the next one; `report` shows an open
  task's last attempt; a journal this build cannot read is moved aside.
- Approvals: `speccoder approvals`, `approve --task`, `reject --task
  --reason`. A decision covers the pending call's class for that task (a
  write's path, a command's exact argv), rides in the attempt's journaled
  input, and never overrides a denial; rejections are told to the model;
  three denials in a row end an attempt as `denied`.
- Inline approvals: at a terminal, `speccoder run` asks about a call that
  needs approval (task, risk, coverage, preview) and continues the same
  attempt; the answer is a journaled effect, so replay never asks again;
  `--no-prompt` keeps the stop-and-approve flow.
- Human controls: `speccoder accept` (a task ticked on a person's word,
  `Verdict: attested`), `skip` (runs pass it by; `--undo`), `nudge` (a note
  for the task's next attempts) and `cost` (tokens per task from `Usage`
  trailers on every speccoder commit; USD with `[model]` prices).
- Live progress: `speccoder run` streams its steps, tool calls and outcome
  (tokens, cost, time) to stderr; `speccoder status` shows the current or
  last run from another terminal (running, interrupted, or its outcome).
- `speccoder init`: detects a project's checks (Cargo with cargo-nextest,
  npm/pnpm/yarn/bun scripts, pytest with ruff and mypy, Go, a Makefile `test`
  target) and writes a commented `speccoder.toml` with narrow
  `[commands] allow` and the nextest JUnit profile; `--force` to replace.
- Gaming monitor (`[monitor] enabled`): a reasoning-blind, judge-side review
  of every passing attempt; a suspicion stops the tick for a person
  (`suspected_gaming`); `eval` reports its precision and recall; an ignored
  calibration test checks it on known gaming and honest diffs.
- `speccoder tui`: a terminal dashboard beside a run — tasks with their
  evidence, the live attempt with its recent tool calls and tokens, and the
  approval queue (`a` approve, `r` reject with a reason).
- MCP client: `[mcp.<name>] command = [...]` stdio servers are started per
  task in the worktree; their tools are offered as `mcp__<server>__<tool>`,
  need approval unless `allow`ed, are hidden when `deny`ed, and replay
  strictly.
- `speccoder skill`: lists the installed Agent Skills and runs Spec Kit's
  planning skills (`specify`, `clarify`, `plan`, `tasks`, `analyze`, …) with
  speccoder's model under a planning policy (Spec Kit's artifacts and scripts
  only), answering clarifying questions inline; implement and converge stay
  `speccoder run` and `converge`.
- `[tests] frozen = "additions"`: new tests may be added to a test file that
  existed before the attempt without approval; changing or removing its
  existing lines still asks (default `"ask"`).
- `provider = "openai-compatible"` with `base_url` (Ollama, vLLM, llama.cpp,
  LM Studio, TGI, …), an optional `api_key_env`, and `structured = "native"`
  (default) or `"tool"`.
- `speccoder workflow install`: a `speccoder` step type for Spec Kit's
  workflow engine (planning skills, or `run`; a stop for a person pauses the
  step, `specify workflow resume` continues) and an example
  specify → plan → tasks → implement workflow.
- Spec Kit extension hooks (`.specify/extensions.yml`): mandatory hooks run
  as hosted skills around hosted skills, `run` and convergence; optional ones
  are offered; conditional ones are left to Spec Kit.
- `[format] argv`: a formatter speccoder runs after each attempt (audited
  like the attempt); `init` writes it for Rust, Go and ruff.
- Spec Kit compatibility matrix: fixtures generated by 0.13.4, 0.15.2,
  0.16.5, 1.0.13, 1.1.3 and 1.2.3, tested on every build; a weekly job tests
  the newest release.
- External executors: `[executor] kind = "claude"` (Claude Code), `"codex"`
  or `"command"` make the attempts; acceptance tests, the integrity audit,
  the checks, retries, the monitor and commits stay speccoder's.
  `speccoder eval --executor` compares them with the native loop.
- OS sandbox for every command speccoder starts (checks, model commands,
  formatter, acceptance tests, mutation tools, MCP servers): Seatbelt on
  macOS; Landlock, seccomp and `no_new_privs` on Linux through speccoder's
  own helper. Writes only to the worktree, a private `TMPDIR` and package
  caches; credentials unreadable; no network beyond loopback.
  `[sandbox] mode`, `network`, `network_allow`, `writable`; a command that
  asks for the network (`"network": true`) needs a person.
- Mutation evidence: `[mutation] tool = "cargo-mutants"` (or any tool writing
  the mutation-testing report schema) on a passing attempt's changes;
  `Mutation:` commit trailer; `mode = "require"` fails on survivors.
- `[budget] best_of = n`: n independent samples per task, the best kept by
  evidence (verdict, survivors, diff size, tokens).
- `speccoder run --parallel N`: ready `[P]` tasks in their own worktrees at
  once, merged into the feature branch and verified together; conflicts run
  again alone, failing together is undone.
- `speccoder pr`: a draft pull request with every task's evidence, after
  confirmation; never merged.
- `speccoder acp`: speccoder as an Agent Client Protocol agent for editors
  (Zed, JetBrains): commands as slash commands, approvals as permission
  requests.
- Crash recovery: an attempt interrupted by a killed process resumes from
  the journal without repeating finished calls; a call that was running is
  not guessed about (the attempt stops `interrupted`); an attempt that had
  finished is judged and ticked; `SPECCODER_CALL_ID` for commands.
- `speccoder eval` replays every recorded attempt strictly and reports it.
- `speccoder bench import`: SWE-bench-format instances as evaluation cases,
  with the benchmark's test patch as the hidden oracle.
- `base_url` for `provider = "openai"` (a gateway in front of the Responses
  API).
- agentplane 0.49.0. Tool results reach the model through agentplane's
  `Transcript`, so every model call is labelled with what the conversation
  read; run inputs are labelled by source (check output, worktree content,
  MCP descriptions); mutating arguments may come only from a closed set of
  sources; argument-less mutating MCP tools are granted exactly `{}`.
- `speccoder replay` and the evaluation suite decide with agentplane's
  `verify`: a faithful replay of a failed or blocked run is `reproduced`;
  `not replayable` (exit 25) is told apart from `diverged` (exit 22).
- MCP tools are discovered with digests; an allowed tool its server changes
  needs approval again until a person approves a call of it.
- Inline prompts (approvals, clarifying questions) wait off the runtime
  thread; a journal in use by another speccoder is refused, never moved aside.
- agentplane 0.50.0. Inputs are admitted with their per-part labels and
  read back with `label_at`; content-based label inference is deleted.
  Refusals relayed to the model carry the label of the call they quote.
- Every approval and rejection — terminal, editor (ACP) or `speccoder
  approve`/`reject` — records who decided, through what and when, in the
  journal, the run report and `approvals.json`.
- An exhausted provider account is refused at once, with the provider's
  code and message (speccoder's own hint for it is gone).
- Documentation site at https://hupe1980.github.io/speccoder/ (built with
  Zola from `site/`): a landing page, a guide from installation to recovery,
  and references for configuration, the CLI and exit codes, with search.
  `SECURITY.md` is now the security policy and links the security model.
- `speccoder.toml` sections speccoder does not know are an error, listing
  the known ones, instead of being ignored.

### Fixed
- A spec changed and committed in the checkout after the speccoder worktree
  was created now reaches the worktree (merged in before the next run).
- A provider error without details (an exhausted credit balance) says where
  to look instead of only "the provider sent an error event".
- Read-only git queries and Spec Kit extension scripts no longer need
  approval in the planning profile; `cwd: "."` and `path: "."` mean the
  workspace; Spec Kit's workflow run state no longer counts as uncommitted.
- An approved edit of a frozen test no longer fails the integrity audit (removed
  tests and skip markers in it still do); absolute paths inside the worktree
  are accepted; a spec without the template's story headings still yields
  acceptance tests; an incomplete attempt is no longer shown as passed.
- A check whose command starts with options (`python3 -m pytest …`) no
  longer allows its bare program (`python3 -c …`) to the model; it allows
  exactly the check.
- A failed or interrupted attempt's changes no longer become the next
  attempt's starting point (its test files were even frozen).
- Acceptance tests no longer pin values that depend on outside state, and
  the attempt is told that constants copied from examples are cheats: a
  hard-coded exchange rate had been verified by red-then-green tests.

- Commands that exit non-zero now show their output to the model (it saw only
  "failed"); `--version` probes no longer need approval; `run` keeps its
  worktree in the state directory it was given. The evaluation cases' specs
  were indented into code blocks, hiding every user story.
